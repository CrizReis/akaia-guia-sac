Configurar o ambiente

O agente de terminal é o motor de tudo o que vem depois. Você escolhe um, instala e confirma que ele responde. Os três funcionam — escolha pelo que você já paga.

1. Escolha o seu agente

Dá pra ter os três instalados. Eles não brigam entre si — cada um é um comando diferente no terminal.

2. Instale

Comece pela página oficial, que tem o instalador do seu sistema. O comando abaixo é o atalho mais comum, mas o site oficial é sempre a fonte certa:

Claude Code · claude.com/claude-code

Rode o comando do agente (claude) e ele abre o navegador pra você entrar na sua conta. É uma vez só por máquina.

Etapa 02 / 07 · Essencial

Instalar a IDE

O terminal sozinho funciona, mas você não enxerga os arquivos. A IDE é a sala onde o agente trabalha: você vê o que ele mudou, abre o resultado e corrige na hora.

1. Entenda a diferença

O agente é quem executa. A IDE é onde você acompanha. São coisas separadas — a mesma IDE roda agentes diferentes, e o mesmo agente roda em IDEs diferentes.

2. Escolha a sua

IDEPerfilNota
OrcaADE — agentes em paraleloa que usamos no treinamento
The MaestriADE — orquestração de agentes—
AntigravityIDE agêntica do GoogleGratuita
CursorIDE — a mais conhecidaPlano pago para uso sério
ZedIDE — leve e muito rápidaGratuita, open source
VS CodeIDE — o padrão da indústriaGratuita, extensão oficial
Nenhuma é obrigatória, mas repare na coluna do meio: ADE é ambiente de agentes, IDE é ambiente de código. Quem vai rodar vários agentes ao mesmo tempo ganha muito com um ADE — é o assunto da etapa 04.

3. Abra uma pasta com o agente dentro

O teste é sempre o mesmo: abra uma pasta qualquer na IDE, chame o agente e peça algo simples — "me diz quantos arquivos tem nessa pasta". Se ele responder certo, a integração está de pé.

Sua entrega

Uma IDE instalada, com uma pasta aberta e o agente respondendo de dentro dela.

Antes de começar

  • Etapa 01 concluída
  • Espaço em disco — IDE ocupa de 300 MB a 1 GB

Etapa 03 / 07 · Essencial

Criar conta no GitHub

É o que te deixa trabalhar com agente sem medo. O agente edita dezenas de arquivos de uma vez — com Git, você vê exatamente o que mudou e volta atrás com um comando.

Por que isso importa pra você

  • Ponto de restauração. Cada commit é um save do jogo. Deu ruim, você volta.
  • Ver o que o agente fez. Em vez de confiar no resumo dele, você lê o antes e o depois.
  • Backup fora da sua máquina. HD queimou, projeto continua.
  • Publicar de graça. O GitHub Pages hospeda site estático sem custo.
  • Pegar skill pronta. Boa parte das skills e plugins de agente mora em repositório.
Três palavras que você vai ouvir o dia todo: repositório é a pasta do projeto versionada; commit é um ponto salvo com uma mensagem do que mudou; push é mandar os commits da sua máquina pro GitHub.

1. Crie a conta

  1. Abra github.com/signup
  2. Use um e-mail que você acessa — o GitHub pede confirmação
  3. Escolha um nome de usuário que você não tenha vergonha de mostrar: ele aparece na URL de tudo que você publicar
  4. Ative a verificação em duas etapas quando ele pedir. É obrigatório pra contribuir, e perder essa conta dá trabalho

2. Instale o Git

A conta é o site; o Git é o programa que roda na sua máquina. Precisa dos dois.

Windows · git-scm.com/download/win
winget install --id Git.Git -e
macOS · com Homebrew
brew install git
Terminal · confirma a instalação
git --version

3. Diga ao Git quem é você

Todo commit é assinado. Use o mesmo e-mail da conta do GitHub:

Terminal · uma vez só por máquina
git config --global user.name "Seu Nome"
git config --global user.email "seu@email.com"

4. Crie seu primeiro repositório

No GitHub, botão New → dê um nome → marque Private se for coisa sua → Create repository. A tela seguinte mostra os comandos pra conectar uma pasta local.

Ou peça ao agente: "cria um repositório pra esse projeto e faz o primeiro commit". Ele conhece os comandos — o que importa é você entender o que está acontecendo.

5. O hábito que salva

Antes de pedir uma mudança grande pro agente, faça um commit. Leva cinco segundos e transforma qualquer erro em algo reversível:

Terminal · salva o estado atual
git add -A
git commit -m "antes de mexer no layout"
Cuidado: nunca mande chave de API, senha ou arquivo .env pro GitHub. Repositório público é indexado por buscador, e chave vazada é chave usada por outro. Use o .gitignore — todo projeto do treinamento já vem com um.

Sua entrega

Conta no GitHub criada e confirmada, git --version respondendo, e um repositório seu com pelo menos um commit.

Antes de começar

  • Um e-mail que você acessa
  • Celular à mão (verificação em duas etapas)
  • Etapas 01 e 02 concluídas

Etapa 04 / 07 · Essencial

O dashboard

Aqui a lógica vira do avesso. Você para de olhar para o código e passa a olhar para quem está trabalhando — quantos agentes estão rodando, no que cada um mexeu e quanto de cota cada um já queimou.

1. IDE e ADE não são a mesma coisa

IDE clássicaADE
Centro da telaO arquivo abertoOs agentes rodando
Você fazEscreve o códigoDistribui e revisa o trabalho
QuantidadeUma tarefa por vezVários agentes em paralelo
ExemplosVS Code, Zed, CursorOrca, The Maestri

ADE é Agent Development Environment — ambiente de desenvolvimento de agentes. O Orca é open source e gratuito, e é o que usamos no treinamento.

2. O painel de agentes

É a tela que dá nome a esta etapa. Nela você vê, lado a lado:

  • Quem está rodando — cada agente ativo na máquina, e em qual tarefa
  • Quanto de cota cada conta já gastou — o número que evita a surpresa de bater o limite no meio de uma entrega
  • O que já terminou e o que está esperando você responder
É normal rodar cinco ou seis agentes ao mesmo tempo. O limite prático não é a máquina — é quanto você consegue revisar. Agente que entrega sem revisão não é produtividade, é dívida.

3. Worktree: por que cada agente ganha a própria pasta

Dois agentes mexendo na mesma pasta se atropelam — um sobrescreve o arquivo que o outro está editando. A solução não foi inventada pela IA: é o git worktree, recurso do próprio Git. Cada worktree é uma branch num diretório separado.

Como fica na prática
projeto/              ← espaço principal, seu branch de trabalho
worktree-landing/     ← agente A, branch própria, não enxerga o B
worktree-whatsapp/    ← agente B, branch própria, não enxerga o A

No Orca, isso é um botão: + no repositório → nome do worktree → escolher o agente. Ele cria o diretório, a branch e sobe o ambiente sozinho.

4. O script de setup — o que separa demo de uso real

Worktree novo nasce sem o que não está versionado: .env, dependências, banco. Por isso cada projeto tem um script de setup, que roda sozinho na criação e faz o feijão com arroz: copia o .env, instala dependências, cria um banco isolado e sobe o ambiente daquele worktree.

Banco isolado por worktree é o detalhe que todo mundo esquece. Sem isso, dois agentes testando ao mesmo tempo escrevem no mesmo banco e um derruba o teste do outro.

5. Revisar antes de aceitar

O ADE mostra o diff — o antes e o depois, linha a linha. É aqui que você para de confiar no resumo do agente e passa a ver o que ele realmente fez. Dá pra comentar uma linha específica e mandar a observação direto pro agente que está rodando, sem interromper.

Terminado e revisado, o worktree é arquivado: a branch é integrada e o diretório, o banco e o ambiente daquela tarefa somem.

6. Quick Commands

Comandos que você salva por projeto — subir o servidor, rodar o formatador, abrir o preview. Ficam rodando em aba própria enquanto você faz outra coisa. É o que evita decorar comando e evita digitar errado na frente da turma.

Sobre o nome: existe o Orca ADE, este app, e existe o segundo cérebro da etapa 06, que em alguns materiais também aparece como Orca. São coisas diferentes — um é onde os agentes trabalham, o outro é o que eles lembram.

Sua entrega

Dois agentes rodando ao mesmo tempo, em worktrees diferentes, visíveis no painel — e um diff revisado por você antes de ser aceito.

Antes de começar

  • Etapas 01 a 03 concluídas
  • O Git instalado — worktree é recurso dele
  • Um repositório pra experimentar

Etapa 05 / 07 · Essencial

Configurar o segundo cérebro

A memória que todos os seus agentes compartilham. É o que separa usar IA de ter uma operação: sem ela, cada conversa recomeça do zero e você explica a mesma coisa pela décima vez.

1. O problema que ele resolve

Segunda-feira você explica ao agente por que escolheu determinada abordagem. Quarta, em outro projeto, ele não sabe de nada — e você explica de novo. Multiplique por todos os projetos, todos os agentes e todos os dias.

O custo não é o tempo de digitar. É que, sem memória, decisão virada não fica virada: o agente sugere de novo o que você já descartou, e você rediscute o mesmo ponto.

2. O que ele guarda — e o que não guarda

EntraPor quê
DecisõesO que foi escolhido e o motivo, pra não rediscutir
PadrõesA solução que funcionou e vale repetir em outro projeto
StackOnde cada coisa fica: qual conta, qual painel, qual caminho
PreferênciasComo você quer que o trabalho seja feito
SessõesO registro do que foi feito em cada dia
O filtro que mantém isso útil: só vira nota o que valer em outro projeto, no futuro. O resto fica no registro do dia. Memória que guarda tudo vira entulho, e entulho não é consultado.

3. Como funciona na prática

Você não pede pra consultar nem pra salvar. Acontece sozinho, em dois momentos:

01

Antes de responder

O agente busca na memória o que tem a ver com o seu pedido e traz pra conversa. Se já existe solução registrada, ele reusa em vez de reinventar.

02

Depois de entregar

Ele registra o que aprendeu — a decisão tomada, o padrão que funcionou, a pegadinha que custou meia hora.

Os dois momentos são automáticos porque ficam presos a gatilhos da ferramenta, não à sua lembrança de pedir. É esse detalhe que faz funcionar: o que depende de disciplina humana diária não sobrevive à segunda semana.

4. Por que ele é compartilhado

A memória não pertence a um agente — pertence a você. O que o Claude registrou na segunda, o Codex lê na quarta. Troca de ferramenta sem perder o acumulado.

5. Onde ele mora

Em arquivos de texto numa pasta sua, não num serviço de terceiro. Isso significa que você consegue abrir, ler, corrigir e versionar no Git — e que ninguém desliga sua memória.

O pacote de configuração será disponibilizado na aula. Ele traz a estrutura de pastas, os gatilhos e o contrato de escrita já prontos. O que está acima é o conceito — chegue entendendo, que a instalação é rápida.

6. O erro mais comum

Tratar o segundo cérebro como arquivo morto — despejar tudo e nunca mais olhar. Memória só vale se for consultada automaticamente antes do trabalho. Se você precisa lembrar de ir lá, ela já falhou.

Sua entrega

O segundo cérebro instalado e um ciclo completo observado: o agente consultou a memória sozinho antes de responder e registrou um aprendizado depois de entregar — sem você pedir nenhuma das duas coisas.

Antes de começar

  • Etapas 01 a 04 concluídas
  • O pacote de configuração da aula
  • Uma pasta decidida pra guardar a memória

Etapa 06 / 07 · Essencial

Criar o projeto

Projeto é uma pasta com contexto. O que separa uma pasta qualquer de um projeto de verdade é o arquivo que explica ao agente onde ele está e como trabalhar ali.

Como o segundo cérebro já está ligado desde a etapa anterior, este projeto nasce com memória: o que você decidir aqui fica disponível nos próximos, e o agente chega sabendo como você trabalha.

1. Crie a pasta

Escolha um lugar fixo pros seus projetos e não espalhe. Pasta de projeto tem milhares de arquivos pequenos — se você tem SSD, é nele que ela deve ficar.

Terminal · cria e entra na pasta
mkdir meu-projeto
cd meu-projeto

2. Abra na IDE e chame o agente

Abra a pasta na IDE da etapa 02 e inicie o agente dentro dela. Tudo o que ele fizer a partir daqui acontece nesse diretório.

3. Gere o arquivo de contexto

É o passo que muda tudo. No Claude Code, o comando é:

No agente · gera o CLAUDE.md
/init

Ele lê a pasta e escreve um CLAUDE.md — o documento que todo agente lê antes de agir. É ali que entra o que o projeto é, como rodar, o que nunca fazer. Pense nele como o manual do cargo: quanto melhor escrito, menos você repete.

4. Versione desde o começo

Terminal · primeiro commit do projeto
git init
git add -A
git commit -m "primeiro commit"
Comece o versionamento antes de o agente escrever muita coisa. Repositório criado depois de três dias de trabalho não te protege dos três dias.

Sua entrega

Uma pasta de projeto com CLAUDE.md gerado, aberta na IDE, versionada com pelo menos um commit.

Antes de começar

  • Etapas 01 a 05 concluídas
  • Uma ideia do que o projeto vai ser

Etapa 07 / 07 · Essencial

Domínio, hospedagem e VPS

Tudo o que você construir precisa de um endereço e de uma máquina pra rodar. São três coisas diferentes, e confundi-las é o erro mais caro de quem está começando — gente que paga VPS pra hospedar uma landing page, ou que compra hospedagem achando que vem com domínio.

1. Os três conceitos, de uma vez

O quêÉ issoAnalogia
DomínioO endereço: seunegocio.com.br. Você aluga por ano.O endereço na rua
HospedagemO espaço onde o site mora, dividido com outros sites.Uma sala alugada no prédio
VPSUm servidor só seu. Você instala o que quiser nele.O prédio inteiro
Os três são independentes. Dá pra ter domínio sem hospedagem, hospedagem sem domínio, e apontar um domínio comprado num lugar para um servidor que está em outro. É exatamente isso que o DNS faz.

2. Qual deles você precisa

Se você vai…Precisa de
Publicar site estático ou landing pageDomínio + GitHub Pages resolve, e é grátis
Rodar WordPress ou lojaDomínio + hospedagem compartilhada
Rodar n8n, Evolution API, banco de dadosDomínio + VPS
Manter agente rodando 24/7Domínio + VPS

Comece pelo mais barato que resolve. Migrar de hospedagem para VPS depois é tranquilo; o que não volta é o dinheiro de um ano de VPS parado.

3. Registrar o domínio

Na Hostinger você pesquisa o nome e registra na mesma tela. Duas coisas que vale saber antes:

  • .com.br é brasileiro. Quem administra é o Registro.br, mesmo que você compre por um revendedor. Em transferência ou problema, é lá que se resolve.
  • Renovação é anual e não perdoa. Domínio expirado sai do ar e pode ser registrado por outra pessoa. Deixe a renovação automática ligada.

4. Apontar o domínio para onde o projeto está

É o passo que liga o endereço à máquina. Dois caminhos:

  • Nameserver — você entrega a gestão inteira do DNS a um provedor. É o mais simples quando domínio e hospedagem estão na mesma empresa.
  • Registro A / CNAME — você mantém a gestão e aponta só o que precisa. O A aponta para um endereço IP (o seu VPS); o CNAME aponta para outro nome (o GitHub Pages, por exemplo).
Propagação: mudança de DNS não é instantânea. Costuma valer em minutos, mas pode levar horas. Antes de achar que deu errado, espere — e teste numa rede diferente, porque o seu computador guarda a resposta antiga em cache.

5. VPS — quando chegar a hora

Você contrata, escolhe um template (sistema já com as ferramentas instaladas) e recebe um IP com acesso administrativo. Dali em diante a máquina é sua: sobe o que quiser, e a conta não muda se rodar um serviço ou dez.

Terminal · acessar o servidor
ssh root@SEU_IP
Servidor é responsabilidade sua. Hospedagem compartilhada tem alguém cuidando da segurança por baixo; VPS não tem. Senha forte, acesso por chave em vez de senha e backup ligado — desde o primeiro dia, não depois do primeiro susto.

Sua entrega

Um domínio registrado no seu nome e a decisão tomada de onde o projeto vai morar — Pages, hospedagem ou VPS.

Antes de começar

  • Um nome de domínio em mente (e alternativas)
  • Cartão ou Pix para o registro
  • Etapa 03 concluída — o Pages depende do GitHub

Extract HTML Design System v2

Transforma o HTML de um site de referência em um design-system.html — biblioteca viva com tipografia, cores, componentes, layout e movimento, reaproveitando as classes originais.

Como usar: copie o prompt, troque [COLOQUE O ENDEREÇO DA PASTA AQUI] pelo caminho da pasta do site e cole no Claude Code.

Prompt · Extract HTML Design System v2
# Extract HTML Design System v2

You are a **Design System Showcase Builder**.
You are given a reference website HTML:
[COLOQUE O ENDEREÇO DA PASTA AQUI]

Your task is to create **one new intermediate HTML file** that acts as a **living design system + pattern library** for this exact design.

---

## GOAL

Generate **one single file** called: `design-system.html` and place it in the same folder of the html file.

This file must preserve the **exact look & behavior** of the reference design by **reusing the original HTML, CSS classes, animations, keyframes, transitions,effects, and layout patterns** — not approximations.

---

## HARD RULES (NON-NEGOTIABLE)

1. Do **not redesign** or invent new styles.
2. Reuse **exact class names, animations, timing, easing, hover/focus states**.
3. Reference the **same CSS/JS assets** used by the original.
4. If a style/component is not used in the reference HTML, **do not add it**.
5. The file must be **self-explanatory by structure** (sections = documentation).
6. Include a **top horizontal nav** with anchor links to each section.

---

## OBJECTIVE

Build a **single page** composed of **canonical examples** of the design system, organized in sections.

---

### 0) Hero (Exact Clone, Text Adapted)

The **first section MUST be a direct clone of the original Hero**:

- Same HTML structure
- Same class names
- Same layout
- Same images and components
- Same animations and interactions
- Same buttons and background
- Same UI components (if any)

**Allowed change (only this):**

- Replace the hero text content to present the **Design System**
- Keep similar text length and hierarchy

**Forbidden:**

- Do not change layout, spacing, alignment, or animations
- Do not add or remove elements

---

### 1) Typography

Create a **Typography section** rendered as a **spec table / vertical list**.

Each row MUST contain:

- Style name (e.g. “Heading 1”, “Bold M”)
- Live text preview using the **exact original HTML element and CSS classes**
- Font size / line-height label aligned right (format: `40px / 48px`)

Include ONLY styles that exist in the reference HTML, in this order:

- Heading 1
- Heading 2
- Heading 3
- Heading 4
- Bold L / Bold M / Bold S
- Paragraph (larger body, if exists)
- Regular L / Regular M / Regular S

Rules:

- No inline styles
- No normalization
- Typography, colors, spacing, and gradients MUST come from original CSS
- If a style uses gradient text, show it exactly the same
- If a style does not exist, do NOT include it

This section must communicate **hierarchy, scale, and rhythm** at a glance.

---

### 2) Colors & Surfaces

- Backgrounds (page, section, card, glass/blur if exists)
- Borders, dividers, overlays
- Gradients (as swatches + usage context)

---

### 3) UI Components
